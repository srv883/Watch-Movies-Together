1. WHAT THIS PROJECT IS
-----------------------
A personal Chrome extension (Manifest V3) that lets two people (Sourav =
usually host, friend Megha = usually guest; old notes/tests say "Priya") watch
the same streaming episode in sync, with chat, emoji reactions, floating
messages, watch history and a live voice call. Peer-to-peer over WebRTC via
PeerJS (lib/peerjs.min.js, v1.5.4); no own server.

How a party links up (V30):
  1. Normal route: PeerJS cloud server (0.peerjs.com) brokers the first
     connection; after that everything is direct P2P.
  2. Automatic backup route (new in V30): if there is no live link for 6 s,
     both sides also meet on public MQTT relays (encrypted with the party
     code) and build the direct connection themselves - no manual codes.
  3. Manual "Direct connect" button (copy/paste codes) still exists.

Supported sites only (since V24): netflix.com, hotstar.com, jiohotstar.com,
primevideo.com, jiotv.com, jiocinema.com.

--------------------------------

What V30 fixed (all found by the new end-to-end test; V29 failed these):
a) SYNC - lost clicks. Each side ignored its own video events for 0.4 s
   after applying a friend's action (to avoid echoing it back), which also
   swallowed REAL clicks in that window: Megha pressing play right after a
   seek, or a speed change right after a friend's seek, were never sent.
   One side ended up playing, the other paused, 9 s apart, forever.
   Fix: exact echo suppression (expectEcho / isEcho): we remember precisely
   which change we applied (play, pause, seek time, rate) and ignore only
   that one event (one-shot, 2.5 s, seek match within 2 s).
b) SYNC - safety net (reconcileWithHost): if the guest's play/pause or speed
   disagrees with the host's heartbeat twice in a row (~8 s) and nobody acted
   for 4 s, the guest adopts the host's state ("Re-synced with ...").
c) RECONNECT - 43 s -> 4 s (acceptIncoming). After a Wi-Fi blip the host kept
   the dead link "open" and refused the friend's re-dial until ICE gave up.
   Now a re-dial from the same friend (or any dial while our link has been
   silent > 6 s) replaces the old link immediately.
d) STATUS: PeerJS server errors no longer flip the panel to "Network hiccup"
   while the party link is actually up.
e) BACKUP ROUTE (AL_* / al* functions): when there is no live link for 6 s,
   both sides connect to the three public MQTT relays in parallel (minimal
   MQTT 3.1.1 client inside content.js), on topic SHA-256("watch-together/
   autolink/topic/" + code). Messages are AES-GCM encrypted with a key
   PBKDF2-derived from the party code; relays see only {v, iv, d} blobs.
   Host offers, guest answers; result = the same direct RTCPeerConnection +
   data channel as manual Direct connect (S.directMode, S.directPC; voice
   rides it). Relays are never opened while PeerJS works and are closed 30 s
   after a healthy link. Chat line when used: "Connected through the backup
   route (PeerJS server unreachable)".
   e2e: PeerJS unreachable from the start -> linked in ~15 s; PeerJS dies +
   link drops -> back in ~14 s; voice works both times.

Voice (unchanged since V29, re-measured on V30):
- Voice call setup over the data link (voffer/vanswer/vice/vbye), legacy
  PeerJS call only for friends older than 1.26.
- Echo cancellation + noise suppression + auto gain ON (NC/headphones

8. HARD-WON RULES / GOTCHAS
---------------------------
- Sync: never ignore video events by a time window - only the exact change
  we applied (V30). Never let play/pause disagreement persist silently.
- The PeerJS server is only needed to START a link: never treat its errors as
  a broken party while linked, and never refuse a friend's re-dial because we
  "still have" a link - it is probably dead (V30).
- PeerJS MediaConnection NEVER emits "open" (V19/V20 total voice failure).
- replaceTrack() is async - await before checking sender.track (redial storm).
- Keep echo cancellation ON with NC (turning it off in V19 caused echo and
  movie leak; the "beeping" was the redial storm).
- Voice-line rules: mute != close; callee always answers with an audio slot;
  host always dials; never redial a healthy line; 5 s redial debounce.
- Opus SDP stereo=0 (mono mic). Chrome DynamicsCompressor adds makeup gain -
  cancelled with LIM_MAKEUP_UNDO.
- Remote WebRTC audio reaches Web Audio only while a media element holds the
  stream - keep #wt-remote-audio attached (muted).
- PeerJS connect() returns undefined when its server is unreachable - guard.
- Direct link: keep S.directPC alive; the channel is already open when
  finishLink/alLinkUp run, so call onConnOpen() manually.
- position:fixed UI must be re-parented into the fullscreen element.
- Harness: fake DOM uses .tag (not .tagName); lone host can't get a mic; when
  editing with node in Git Bash, Windows backslash paths and \u escapes get
  mangled - use the Edit tool.
- In the relay-encryption test, check payload SHAPE and non-base64 markers;
  plain words can appear by chance inside random base64.
